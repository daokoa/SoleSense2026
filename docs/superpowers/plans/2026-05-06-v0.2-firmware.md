# SoleSense v0.2 Firmware Implementation Plan

> **Status:** in progress. Foundational scaffold landed at `firmware/SoleSenseV2/`. v0.1 (`firmware/SoleSense/`) is untouched and remains the demo path.

**Goal:** rewrite the v0.1 raw-CSV recording pipeline into the v0.2 architecture: incremental FFT + top-N outlier buffer in MCU RAM, multi-slot ring buffer in flash, pause-on-disconnect, no browser-side state.

**Design reference:** [`docs/superpowers/specs/2026-05-06-v0.2-data-architecture.md`](../specs/2026-05-06-v0.2-data-architecture.md)

**Architecture:** the sketch is broken into focused modules (one .h/.cpp pair each). The .ino is a thin top-level. v0.1's single 522-line .ino was fine for one person; v0.2 is meant to be parallelizable across the software team.

**Tech stack:** unchanged from v0.1 -- Arduino + ESP32-C3 core, ESPAsyncWebServer, LittleFS, Preferences, Wire.

### Task 4 -- FFT module (Goertzel) -- `fft.cpp` [x] DONE

Implementation:

- Windowed Goertzel: each (channel, bin) accumulates `q1`, `q2` for FFT_WIN_SIZE = 256 samples (~=5 s at 50 Hz), then magnitude is read out, state is reset, and the next window begins. Most-recent magnitude is cached in `sMag[c][b]` for O(1) reads.
- Per-bin precomputation: `cos(omega)`, `sin(omega)`, and `coef = 2.cos(omega)` (one of each per bin, shared across channels).
- DC removal: `running_mean` parameter passed in by `SoleSenseV2.ino` (Welford running mean) is subtracted from each sample before processing. Eliminates the FSR ADC offset / accel-Z gravity leakage into low-frequency bins.
- Outliers excluded: if a sample is flagged by the outlier detector, the FFT update is skipped for that channel that tick (so injury-causing spikes don't smear the spectrum).
- Magnitude formula uses real + imaginary components:
  ```
  real = q1 - q2 * cos(omega)
  imag = q2 * sin(omega)
  magnitude = sqrt(real^2 + imag^2) * 2 / N
  ```
  The `2/N` scaling makes a unit sine wave at the bin centre read magnitude 1.0 (single-sided amplitude).

Validation:

- Numerical reference: Python equivalent run against the same on-bin synthetic signal, agreement to 0.0000% -- math is exact.
- On-device self-test: `fft_self_test()` feeds a 1.953 Hz sine (k=10 on the 256-bin grid at 50 Hz) at amplitude 100 with DC offset 500 into channel 0. Expected: ~100 mag at the closest bin, all others  100. Off-bin signals (e.g. 2.00 Hz exact) will spread ~10% of energy to neighbours -- that's correct DSP, not a bug.
- HTTP-trigger: `POST /api/fft-selftest` runs the self-test; output goes to Serial Monitor.

Tunables left for whoever picks up Task 6:
- Window length (FFT_WIN_SIZE = 256 -> 5 s update interval). Could shorten with overlap for faster spectrum updates if the report UI feels laggy.
- Bin frequency table (in `fft.cpp`). Quantised to nearest representable bin internally. Tune per-channel if the team wants different bins for FSR vs IMU axes.

### Task 5 -- Storage module (multi-slot ring buffer) -- `storage.cpp` [x] DONE

Implementation:

- **Per-slot files** (not one big seekable file): `/run_slot_0.bin` ... `/run_slot_9.bin`. Simpler, more LittleFS-friendly, every save is `open("w") + write + close` so a power-cut leaves only the slot in progress in a corrupt state -- the previous 9 are untouched.
- **Slot layout**: `[SlotHeader (24 B)] [body (~3 KB)] [SlotTrailer (8 B)]`. Body is FFT magnitudes + outlier buffer + 32 bytes reserved meta. Total ~3 KB per slot, well under the 10 KB cap.
- **Atomic-ish guarantee**: trailer carries `crc32` over header+body and a `magic` complete-marker. Power-cut mid-write leaves either no trailer (file too short) or a partial trailer (magic wrong) or a present trailer with mismatched CRC -- all three rejected by the loader.
- **CRC32**: self-contained IEEE 802.3 implementation, no platform header. Validated against `zlib.crc32` byte-for-byte on multiple test cases.
- **Ring rotation**: `sNextSlot` round-robins 0..9; `sSlotSeq` is a monotonic counter stored in the header (so even after the ring wraps, the loader picks the newest by sequence, not by file order).
- **Resume on boot**: `storage_init()` calls `storage_load_latest()` and seeds `sSlotSeq` to one past the highest seen, so post-reboot writes don't collide with pre-reboot data.

Self-test (`storage_self_test()` / `POST /api/storage-selftest`):

1. Writes 3 slots with sequence numbers 100, 101, 102.
2. Confirms `load_latest()` returns slot with `slot_n=102`.
3. Deliberately overwrites the slot 2 trailer with garbage (simulating a power-cut mid-write).
4. Confirms `load_latest()` now returns the slot with `slot_n=101` (correctly rejected the corrupted one).
5. Cleans up.

Output goes to Serial Monitor; HTTP response is just an ack.

Diagnostic: `GET /api/storage-state` returns `{valid_slots, latest:{slot_n, timestamp_ms, sample_count, run_done}}`.

Tunables left for later:
- Body content currently stores FFT magnitudes only (not the in-progress q1/q2 recurrence state). Reconnect-resume will be lossless for the most-recent finalized window but loses the partial-window samples accumulated since the last finalize. Acceptable since FFT_WIN_SIZE = 256 = 5 s and STORAGE_FLUSH_MS = 3000 = 3 s -- flushes are more frequent than window-finalizes anyway.
- 10 slots x 3 s = 30 s of recoverable history. Tune `STORAGE_SLOT_COUNT` and `STORAGE_FLUSH_MS` together if more or less is wanted.

### Task 6 -- HTTP routes -- `http_routes.cpp` [x] DONE

`/api/run-report` now computes real metrics from the FFT bins, outlier buffer, and per-channel running stats. Output shape matches what `software/frontend/solesense-v1/index.html`'s `render(r)` consumes -- the dao UI's existing report screen renders directly from this response, no JS changes needed for v0.2.

Metrics computed:

| Metric | Source |
|---|---|
| `cadence` | Peak FFT bin in heel channel (FSR 0) within the 1-4 Hz stride band, x 60 |
| `zoneAvg.{heel,midfoot,ball,toe}` | Per-channel running mean from `stats_get_mean()` |
| `lPct` / `rPct` | Medial-vs-lateral split of FSR running means |
| `heel_strike` flag | heel/forefoot load ratio > 65% AND heel - ball > 10 |
| `loadingRate` | Largest FSR-channel outlier sigma x 10 (proxy; calibration TBD) |
| `pronate` | Running mean of gyro-x (first-order -- full per-stride integration would need time-domain access we don't keep) |
| `contactMs` | 35% of stride period (proxy; team can refine) |
| `steps` | `strideHz * durSec` |

Flag thresholds match v0.1 dao's `THRESH` constants exactly:
- `cadence_low: 160`  -> `low_cadence`
- `loading_high: 60`  -> `high_loading`
- `pronate_high: 15`  -> `overpronation`
- `supinate_low: -8`  -> `supination`
- `asym_high: 10`     -> `bilateral_asym`
- `contact_high: 300` -> `contact_long`
- heel ratio > 65 + heel-ball > 10 -> `heel_strike`

Validation: Python equivalent run against three synthetic cases (clean run, heel-striker with low cadence + overpronation, asymmetric supinator). All flags fire as expected for each case.

Stats infrastructure: extracted Welford running mean/variance into `stats.h/.cpp` so the FFT (DC removal), outlier detector (sigma threshold), and report analysis all read from one source of truth.

Open refinements for the team:
- Loading-rate scaling factor (currently `sigma x 10`) is empirical. Calibrate against a known impact event when sensors are wired.
- Pronation accuracy. Mean gyro-x is the simplest indicator but ignores per-stride timing. Better: track cumulative gyro-x integral within outlier-bracketed stance windows.
- Contact-time accuracy. Currently 35% of stride period. Per-stride heel-strike -> toe-off detection in the time domain would be precise, but requires a circular sample buffer we don't currently keep.

# SoleSense v0.2 Firmware Implementation Plan

> **Status:** in progress. Foundational scaffold landed at `firmware/SoleSenseV2/`. v0.1 (`firmware/SoleSense/`) is untouched and remains the demo path.

**Goal:** rewrite the v0.1 raw-CSV recording pipeline into the v0.2 architecture: incremental FFT + top-N outlier buffer in MCU RAM, multi-slot ring buffer in flash, pause-on-disconnect, no browser-side state.

**Design reference:** [`docs/superpowers/specs/2026-05-06-v0.2-data-architecture.md`](../specs/2026-05-06-v0.2-data-architecture.md)

**Architecture:** the sketch is broken into focused modules (one .h/.cpp pair each). The .ino is a thin top-level. v0.1's single 522-line .ino was fine for one person; v0.2 is meant to be parallelizable across the software team.

**Tech stack:** unchanged from v0.1 — Arduino + ESP32-C3 core, ESPAsyncWebServer, LittleFS, Preferences, Wire.

Acceptance: compiles in Arduino IDE; flashing it brings up the AP; `GET /api/run-state` returns a JSON stub.

### Task 2 — Wire sensor reads into the run loop

`sensors.cpp` is already complete (copied from v0.1). What's left:
- In `loop()`, when `gNewSample` flag set AND `gRunActive==true`, call `readAllFsr()` + `readImu()`, then push results into the FFT and outlier modules.
- The 50 Hz hardware-timer ISR (lifted from v0.1) sets `gNewSample`.

This is plumbing, not new logic. Should be straightforward once Task 4 + 5 land.

### Task 3 — Pause-on-disconnect logic in `state.cpp`

Per the v0.2 spec §7:
- `WiFi.softAPgetStationNum()` checked once per loop iteration.
- When stations==0 and `gRunActive==true`, set `gRunActive=false`, log "[Run] paused", but keep state in RAM.
- When stations>0 and run was paused, resume: set `gRunActive=true`, log "[Run] resumed".
- `gRunElapsedMs` only advances during active intervals — accumulated in `state.cpp` from delta times.

Acceptance: with phone on/off the AP, Serial Monitor shows the pause/resume markers and `/api/run-state.elapsed_ms` only advances during connected windows.

### Task 4 — FFT module (Goertzel) — `fft.cpp`

Currently stubbed. Real implementation:
- For each FSR channel (6) and each gyro/accel axis (6), maintain a fixed set of Goertzel bin states.
- Bins to track (initial guess, tune later):
  - 0.5 Hz (very-low: posture drift)
  - 1.0–4.0 Hz in 0.25 Hz steps (stride-fundamental + first 2 harmonics)
  - 5.0, 7.5, 10.0, 12.5, 15.0 Hz (impact transients, footstrike high-frequency content)
- That's roughly 18 bins × 12 channels = 216 bins. Each bin is 3 floats of state plus the running coefficient. ~9 KB of RAM. Comfortable.
- Per-sample update: for each bin, run the standard Goertzel recurrence:
  ```
  s_new = sample + coeff * s_prev1 - s_prev2;
  s_prev2 = s_prev1;
  s_prev1 = s_new;
  ```
- Magnitude on demand: `sqrt(s_prev1² + s_prev2² - coeff*s_prev1*s_prev2)`.

Acceptance: `getFftMagnitude(channel, freqHz)` returns sane numbers for a known synthetic signal in unit testing.

### Task 5 — Storage module (multi-slot ring buffer) — `storage.cpp`

Slot layout per spec §4. ~10 slots in `/run.bin` (single LittleFS file used as a slotted container). Each slot ~10 KB, total ~100 KB. Plenty of headroom in the 1.5 MB partition.

Implementation:
- `storage_save_snapshot()`: serialize `{header, fft state, outliers, meta, trailer}` into a buffer; seek to next slot offset; write; advance ring index.
- `storage_load_latest()`: scan all slots' headers, validate trailers (CRC32 + magic byte), pick highest valid timestamp.
- `storage_init()`: open or create `/run.bin`, pre-allocate to fixed size if missing.
- CRC32 via the ESP32 ROM `crc32_le()` function.

Acceptance: simulate a power-cut by killing the device mid-write; on next boot, `storage_load_latest()` returns the slot before the failed one with no data corruption.

### Task 6 — HTTP routes — `http_routes.cpp`

Headers are defined; simple routes (`/api/device`, `/api/sensor`, `/api/start`, `/api/stop`, `/api/sleep`) are easy ports from v0.1.

The new routes that need real bodies:
- `GET /api/run-state` — `{recording, run_active, elapsed_ms, sample_count, last_flush_age_ms, clients_connected}`. Reads from state.cpp + storage.cpp.
- `GET /api/run-spectrum` — JSON of the current FFT bins per channel (downsampled if needed for response size).
- `GET /api/run-outliers` — JSON of the current outlier buffer.
- `GET /api/run-report` — runs analysis on the FFT + outliers and returns final metrics (cadence, GCT, pronation, L/R balance, injury flags, pressure distribution). The most logic-heavy route.

`POST /api/calibrate/zero` and `POST /api/calibrate/imu` work the same way they do in v0.1. `POST /api/settings` — keep but ignore the threshold inputs (all hardcoded now).

`GET /data.csv` is **dropped** from v0.2 by default. If the team wants CSV export, MCU reconstitutes a simulated CSV from the FFT.

### Task 7 — Frontend integration

The dao UI from v0.1 mostly works against v0.2 with minor changes:
- Stop polling `/api/sensor` constantly during recording. Instead poll `/api/run-state` for the timer and aggregate stats.
- Drop the local `sensorData` JS array and the JS-side analysis pipeline. Everything comes from `/api/run-report`.
- Show "Paused" state in the UI when `run_state.run_active==false`.

This is a frontend change but non-blocking — v0.1 dao still works against v0.1 firmware for the demo.

### Task 8 — Hardware verification

End-to-end smoke test on the XIAO with phone:
- Start a run, see the live timer.
- Disconnect phone for 30 seconds.
- Reconnect; confirm timer paused and resumed exactly.
- Stop, see report. Confirm cadence/GCT/etc come from the MCU not browser-side computation.

If you're picking up Task 6 (HTTP routes) — start in `http_routes.cpp`. Most of the simple routes are already done; the heavy lift is `/api/run-report`.

Tasks 4 and 5 are independent — can be parallelized across two people. Task 6 depends on 4+5 being functional enough to query.

# v0.2 Data Architecture — MCU as Source of Truth

## Problem with v0.1

In v0.1 the recording flow has data living in two unsafe places:

- **Andony's UI**: phone polls `/api/sensor` at 5 Hz and accumulates samples in a JS array in browser memory. WiFi blip → array half-full → run lost.
- **Dao's UI / firmware backend**: 50 Hz raw CSV streamed to LittleFS, downloaded to the phone after `/api/stop` for client-side analysis. Slightly safer than Andony's path because the data is on the MCU, but still fragile during the run — the phone's timer drifts from the MCU's, and the analysis code lives in JS where it can't run if the page closes.

Either way: a momentary disconnection during a run cooks the data, and the phone holds state it shouldn't.

## v0.2 directive

**Nothing is stored on the device that's streaming the website (i.e. the phone/browser).** The MCU is the only place data lives. Phone is a viewer that asks the MCU what to render.

This means:

1. The phone-side `sensorData` array is gone.
2. The phone-side run timer is gone — MCU reports elapsed time.
3. The phone-built CSV download path is gone — if a CSV export is wanted, the MCU streams it.
4. On disconnect/reconnect, the phone re-queries the MCU and continues from wherever the device's state machine actually is.

## Pipeline

```
Sensors @ 50–100 Hz
        │
        ▼
   ┌────────────────────────────────┐
   │ MCU RAM                         │
   │  ├── Live FFT coefficients (~3000 sine terms)        │
   │  ├── Top-N outlier buffer (capacity ~100)             │
   │  └── Run metadata (start_ms, sample_count, …)         │
   └────────────────────────────────┘
        │  every ~3 seconds (benchmark; tune later)
        ▼
   ┌────────────────────────────────┐
   │ MCU LittleFS                    │
   │  Multi-slot ring buffer (~10 slots).   │
   │  Each slot = one snapshot of {coefs, outliers, meta, header, trailer}. │
   │  Newest-valid is found by header timestamp; trailer checksum proves the write completed. │
   └────────────────────────────────┘
        │  on demand (`GET /api/run-state` etc)
        ▼
   Phone (viewer only)
```

### 1. Sample into RAM (no raw 50 Hz stream is ever stored)

We continue sampling at 50–100 Hz internally (rate TBD; see "Decisions still open" below) but **never write the raw stream to flash**. Earlier math showed raw 50 Hz blows the 1.5 MB partition in ~5 minutes; raw 100 Hz fills it in ~2.5 minutes. Storing every sample is unaffordable, so we don't.

### 2. Decompose into a Fast Fourier Transform (FFT)

Any time-series signal can be expressed as a sum of sine waves. Practically you cap that sum — say 3000 terms — and pick a target error rate (e.g. ≤1%). Each new sample updates those 3000 coefficients incrementally instead of being stored individually.

> *"3000 sign waves represent the entire run."*

What this buys us:

- **Bounded RAM**: storage cost is fixed (3000 × bytes-per-coefficient) regardless of run length. A 1-minute run and a 60-minute run consume the same memory.
- **Bounded flash**: same applies to the persisted snapshot.
- **Frequency-domain features come free**: cadence, stride frequency, dominant gait frequency are coefficients in the transform — no separate detection step needed.

### 3. Outliers go in a separate list

Outliers (samples > N σ from local mean, or peak detections that exceed a threshold) are **excluded from the FFT** because they would skew the spectrum, AND they are the most clinically interesting moments — heel-strike spikes, asymmetric load events, sudden impacts.

So we maintain a **fixed-capacity top-N outlier buffer** (~100 entries) alongside the FFT coefficients. When the buffer is full, evict the smallest by magnitude.

> *"You don't count it. … you have a separate space for top 100 outliers."*

Each outlier entry: `{timestamp_ms, sensor_id, value, type}`.

### 4. Flash flush: multi-slot ring buffer with atomic-write semantics

Every ~3 seconds, copy the RAM state into a new flash slot.

**Why a ring buffer instead of overwrite-in-place:**

- Mid-write crash leaves the file half-written. If we always wrote to the same slot, a single crash corrupts everything. A ring buffer means the previous slot is still intact.
- Wear-levels writes across slots (LittleFS already does some of this; ring buffer is belt-and-suspenders).

**Slot count**: ~10 slots. ~30 seconds of recoverable history. Tune later.

**Slot layout**:
```
┌──────────────────────────────────────┐
│ Header  : { slot_n, timestamp_ms,    │
│            schema_version, length }   │
├──────────────────────────────────────┤
│ Body    : FFT coefficients +          │
│           outlier buffer +            │
│           run metadata                │
├──────────────────────────────────────┤
│ Trailer : { crc32 over header+body,   │
│            magic_complete }           │
└──────────────────────────────────────┘
```

**On boot or reconnect:**
1. Scan all 10 slots.
2. Discard any slot whose trailer's `magic_complete` isn't set, or whose CRC doesn't match (incomplete write).
3. Pick the slot with the highest header timestamp from what's left. That's the newest known-good save.

> *"How do you know if the file was finished saving? … Compare it to the last … At the top of the file, you have a writing thing."*

### 5. HTTP API (phone ↔ MCU)

| Endpoint | Purpose |
|---|---|
| `POST /api/start` | Start a run. MCU resets RAM state, marks `recording=true`. |
| `POST /api/stop`  | End run. MCU does a final flash flush. |
| `GET /api/run-state` | Returns `{recording, elapsed_ms, sample_count, last_flush_age_ms}`. Phone polls this for the live timer + any live aggregates. |
| `GET /api/run-spectrum` | Returns the current FFT coefficients (or a downsampled summary for display). |
| `GET /api/run-outliers` | Returns the current outlier buffer. |
| `GET /api/run-report` | Returns the analysed metrics computed on-MCU from the FFT + outliers (cadence, GCT, pronation, L/R balance, injury flags, pressure distribution). |
| `GET /data.csv` | Optional. If we want CSV export, MCU reconstitutes a sampled stream from the FFT and serves it. The phone never builds CSVs anymore. |

The phone NEVER caches any of this. Each navigation re-queries.

### 6. Reconnect flow

1. Phone loses WiFi briefly. JS state may be wiped (depending on whether the page reloads).
2. Phone reconnects to the SoleSense AP.
3. Page loads, calls `GET /api/run-state`.
4. If `recording=true`, page resumes the live UI from `elapsed_ms`.
5. If `recording=false` and a finished run exists in flash, page goes to the report screen and pulls `/api/run-report`.

No data lost. Phone is a thin viewer.

## Why FFT (vs. averaged downsampling)

We had originally planned 50 Hz → 5 Hz averaged writes for v0.2. The team's call: that throws away the high-frequency content (loading-rate spikes, heel-strike transients) which are exactly the injury signals. FFT keeps the spectrum, and outliers in a separate buffer keep the actual peak events.

Net: averaged-downsampling is being **replaced** by FFT-coefficients + outlier-buffer in v0.2.

## Implementation sketch (firmware, rough)

- New module: `solesense_fft.h/cpp`. Maintains a sliding-window or recursive incremental FFT (Goertzel for individual bins is one option; a true sliding-DFT is another). Capacity 3000 coefficients.
- New module: `solesense_outliers.h/cpp`. Fixed-capacity heap; insert with eviction.
- New module: `solesense_storage.h/cpp`. Multi-slot writer; load-newest-valid on boot.
- `takeSample()` change: instead of formatting CSV row → ring buffer → file, it pushes the sample into the FFT and the outlier detector.
- `loop()` change: in addition to draining `gNewSample`, every 3 s call `flushSnapshot()`.
- New routes per the table above; deprecate `/data.csv` raw streaming.

## Decisions still open

These need a team conversation:

1. **Sample rate**: 50 Hz (current) or 100 Hz? Andony argued 50 Hz is "the standard" but other devices (Pedar-X, Moticon OpenGO) sample at 100 Hz internally. With FFT-based storage, the cost of higher rates is just more compute, not more flash. Lean 100 Hz unless CPU budget is too tight.
2. **FFT type**: full DFT, sliding-DFT, Goertzel, or Welch's method? Each has different RAM/CPU/accuracy tradeoffs. Need a numerical-methods sanity check from someone — possibly worth a 1-day prototype.
3. **3000 coefficient count**: arbitrary upper bound mentioned in the discussion. Real number depends on sample rate and target error rate. Probably much smaller in practice (e.g., 256–512 bins capture everything below 25 Hz at 50 Hz sample rate).
4. **Slot count and flush interval**: 10 slots × 3 s = 30 s recoverable. Adequate? Or do we want longer?
5. **Outlier definition**: σ-threshold? Peak-of-derivative? Domain-specific (e.g. heel-strike acceleration peak)? Need to pin this before implementation.
6. **Time sync**: do we need wall-clock time at all, or does `millis()` since boot suffice? If runs span deep-sleep cycles, RTC will be needed.

## What this means for v0.1

v0.1 ships as-is. v0.2 is a planned rewrite of the data path; nothing about the wiring, the AP, the boot sequence, or the calibration changes. The API surface gains new endpoints and `/data.csv` becomes optional.

## What this means for the team

- **Firmware**: adds the three new modules above; this is the biggest piece of v0.2 work.
- **Frontend**: simpler, not more complex. The Andony 5-Hz polling JS goes away; `sensorData` array goes away; CSV export goes away. The page just renders what `/api/run-state` and `/api/run-report` return.
- **Hardware/electrical**: no change.
- **Mechanical**: no change.

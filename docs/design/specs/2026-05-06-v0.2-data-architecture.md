# Data Architecture -- MCU as Source of Truth

## The problem this design solves

A naive recording flow leaves data living in two unsafe places:

- **Browser-polling UI**: the phone polls `/api/sensor` at 5 Hz and accumulates samples in a JS array in browser memory. WiFi blip -> half-full array -> lost run.
- **CSV-streaming firmware**: raw CSV streams to LittleFS and is downloaded to the phone after `/api/stop` for client-side analysis. Slightly safer than the browser-polling path because the data lives on the MCU, but still fragile during the run -- the phone's timer drifts from the MCU's, and the analysis code lives in JS, which can't run if the page closes.

Either way, a momentary disconnection during a run cooks the data, and the phone holds state it shouldn't.

## Directive

**Nothing is stored on the device that streams the website (i.e. the phone/browser).** The MCU is the only place data lives. The phone is a viewer that asks the MCU what to render.

This means:

1. The phone-side `sensorData` array is gone.
2. The phone-side run timer is gone -- the MCU reports elapsed time.
3. The phone-built CSV download path is gone -- if a CSV export is needed, the MCU streams it.
4. On disconnect/reconnect, the phone re-queries the MCU and resumes from whatever state the device's state machine is in.

## Pipeline

```
Sensors @ 50-100 Hz
        |
        
   ,--------------------------------.
   | MCU RAM                         |
   |  |-- Live FFT coefficients (~3000 sine terms)        |
   |  |-- Top-N outlier buffer (capacity ~100)             |
   |  `-- Run metadata (start_ms, sample_count, ...)         |
   `--------------------------------'
        |  every ~3 seconds (benchmark; tune later)
        
   ,--------------------------------.
   | MCU LittleFS                    |
   |  Multi-slot ring buffer (~10 slots).   |
   |  Each slot = one snapshot of {coefs, outliers, meta, header, trailer}. |
   |  Newest-valid is found by header timestamp; trailer checksum proves the write completed. |
   `--------------------------------'
        |  on demand (`GET /api/run-state` etc)
        
   Phone (viewer only)
```

### 1. Sample into RAM (no raw 50 Hz stream is ever stored)

We keep sampling at 50-100 Hz internally (rate TBD; see "Decisions still open" below) but **never write the raw stream to flash**. Earlier math showed raw 50 Hz fills the 1.5 MB partition in ~5 minutes and raw 100 Hz fills it in ~2.5 minutes. Storing every sample is unaffordable, so we don't.

### 2. Decompose into a Fast Fourier Transform (FFT)

Any time-series signal can be expressed as a sum of sine waves. In practice you cap that sum -- say 3000 terms -- and pick a target error rate (e.g. <=1%). Each new sample updates those 3000 coefficients incrementally instead of being stored individually.

> *"3000 sign waves represent the entire run."*

What this buys us:

- **Bounded RAM**: storage cost is fixed (3000 x bytes-per-coefficient) regardless of run length. A 1-minute run and a 60-minute run use the same memory.
- **Bounded flash**: the same applies to the persisted snapshot.
- **Frequency-domain features come for free**: cadence, stride frequency, and dominant gait frequency are coefficients in the transform -- no separate detection step needed.

### 3. Outliers go in a separate list

Outliers (samples > N sigma from the local mean, or peak detections that exceed a threshold) are **excluded from the FFT** because they would skew the spectrum. They are also the most clinically interesting moments -- heel-strike spikes, asymmetric load events, sudden impacts.

So we maintain a **fixed-capacity top-N outlier buffer** (~100 entries) alongside the FFT coefficients. When the buffer fills, evict the smallest entry by magnitude.

> *"You don't count it. ... you have a separate space for top 100 outliers." — David the Benevolent King*

Each outlier entry: `{timestamp_ms, sensor_id, value, type}`.

### 4. Flash flush: multi-slot ring buffer with atomic-write semantics

Every ~3 seconds, copy the RAM state into a new flash slot.

**Why a ring buffer instead of overwrite-in-place:**

- A mid-write crash leaves the file half-written. If we always wrote to the same slot, a single crash would corrupt everything; a ring buffer keeps the previous slot intact.
- It spreads writes across slots for wear-leveling (LittleFS already does some of this; the ring buffer is belt-and-suspenders).

**Slot count**: ~10 slots, giving ~30 seconds of recoverable history. Tune later.

**Slot layout**:
```
,--------------------------------------.
| Header  : { slot_n, timestamp_ms,    |
|            schema_version, length }   |
|--------------------------------------+
| Body    : FFT coefficients +          |
|           outlier buffer +            |
|           run metadata                |
|--------------------------------------+
| Trailer : { crc32 over header+body,   |
|            magic_complete }           |
`--------------------------------------'
```

**On boot or reconnect:**
1. Scan all 10 slots.
2. Discard any slot whose trailer's `magic_complete` isn't set or whose CRC doesn't match (incomplete write).
3. From what's left, pick the slot with the highest header timestamp. That's the newest known-good save.

> *"How do you know if the file was finished saving? ... Compare it to the last ... At the top of the file, you have a writing thing."*

### 5. HTTP API (phone <-> MCU)

| Endpoint | Purpose |
|---|---|
| `POST /api/start` | Start a run. MCU resets RAM state, marks `recording=true`. |
| `POST /api/stop`  | End run. MCU does a final flash flush. |
| `GET /api/run-state` | Returns `{recording, run_active, elapsed_ms, sample_count, last_flush_age_ms, clients_connected}`. `elapsed_ms` is the value from the latest valid flash slot -- not a wall-clock since `/api/start`. `run_active` is true only when at least one client is on the AP and sampling is advancing. The phone polls this for the live timer. |
| `GET /api/run-spectrum` | Returns the current FFT coefficients (or a downsampled summary for display). |
| `GET /api/run-outliers` | Returns the current outlier buffer. |
| `GET /api/run-report` | Returns the analyzed metrics computed on-MCU from the FFT + outliers (cadence, GCT, pronation, L/R balance, injury flags, pressure distribution). |
| `GET /data.csv` | Optional. If CSV export is wanted, the MCU reconstitutes a sampled stream from the FFT and serves it. The phone never builds CSVs anymore. |

The phone NEVER caches any of this. Every navigation re-queries.

### 6. Reconnect flow

1. The phone loses WiFi briefly. JS state may be wiped, depending on whether the page reloads.
2. The phone reconnects to the SoleSense AP.
3. The page loads and calls `GET /api/run-state`.
4. If `recording=true`, the page resumes the live UI from the `elapsed_ms` the MCU reports.
5. If `recording=false` and a finished run exists in flash, the page goes to the report screen and pulls `/api/run-report`.

No data lost. The phone is a thin viewer.

### 7. Connection-aware time keeping (the duration timer rules)

Two firm rules from the team:

> **The duration timer pauses when the phone disconnects.**
> **Duration is derived from what's actually saved to flash, not from a wall-clock since `/api/start`.**

This rules out the naive `elapsed_ms = millis() - run_start_ms` approach. Instead:

**Source of truth for elapsed time** = `latest_valid_flash_slot.run_elapsed_ms`.

In other words, the MCU flushes a snapshot to flash every ~3 s. Each snapshot has a `run_elapsed_ms` field in its header. The `/api/run-state` endpoint returns the value from the most recent valid slot -- never a more-up-to-date in-RAM number that hasn't been persisted yet. So if the phone disconnects mid-flush, on reconnect it sees the duration as of the last successful flush, which matches the duration of the data that actually survives.

**Pause-on-disconnect mechanism** (firmware):

```
loop():
    clients = WiFi.softAPgetStationNum()
    if recording:
        if clients > 0:
            # phone (or some client) is connected
            run_active = true
            # sample, update FFT, increment outlier counts as usual
            if (millis() - last_flush_ms) >= FLUSH_INTERVAL_MS:
                run_elapsed_ms += (millis() - last_active_ms)
                last_active_ms = millis()
                flush_to_next_slot(run_elapsed_ms)
        else:
            # nobody watching -- pause
            run_active = false
            last_active_ms = millis()   # so the elapsed-ms calc skips this gap on resume
```

In plain English: the MCU only advances `run_elapsed_ms` while at least one client is connected to the AP. While the AP is empty, nothing is sampled into the FFT, no flushes happen, and the elapsed counter doesn't grow. When the phone comes back, sampling resumes and the next flush picks up where the previous one left off.

**Why client-count instead of a JS heartbeat:** it's simpler. The AP already knows when stations come and go via 802.11, so no extra ping endpoint is needed.

**Why pause sampling (not just pause the timer):** because the user told us "the only data saved are these transforms in flash." If we kept sampling during a disconnect and folded those samples into the FFT, we'd pollute the transform with noise from a period the user can't see and didn't authorize. Pausing both keeps the transform clean.

**Edge cases:**

- Phone disconnects exactly during a flush. The flush completes (it's a single `LittleFS` write that takes ms, not seconds), the slot's CRC trailer is written, and the slot is valid. Reconnect picks it up. No corruption.
- Phone never reconnects. After `/api/stop`, the MCU writes a final slot with `run_done=true`. The data sits in flash until either `/api/data/clear` or the next `/api/start`.
- Multiple clients connect (e.g. laptop + phone). Recording continues as long as >= 1 client is on the AP; the last client to disconnect triggers the pause.
- Phone connects without ever loading the page. We pause based on AP station count, not page state, so this still counts as "connected." For stricter behavior, switch to a JS heartbeat. Open question.

## Why FFT (vs. averaged downsampling)

We had originally planned 50 Hz -> 5 Hz averaged writes for v0.2. The team's call: that throws away the high-frequency content (loading-rate spikes, heel-strike transients) which is exactly the injury signal. The FFT keeps the spectrum, and a separate outlier buffer captures the actual peak events.

Net: averaged downsampling is **replaced** by FFT coefficients + an outlier buffer in v0.2.

## Implementation sketch (firmware, rough)

- New module `solesense_fft.h/cpp`: maintains a sliding-window or recursive incremental FFT (Goertzel for individual bins is one option; a true sliding-DFT is another). Capacity 3000 coefficients.
- New module `solesense_outliers.h/cpp`: fixed-capacity heap; insert with eviction.
- New module `solesense_storage.h/cpp`: multi-slot writer; load-newest-valid on boot.
- `takeSample()` change: instead of formatting a CSV row -> ring buffer -> file, push the sample into the FFT and the outlier detector.
- `loop()` change: in addition to draining `gNewSample`, call `flushSnapshot()` every 3 s.
- New routes per the table above; deprecate `/data.csv` raw streaming.

## Decisions still open

These need a team conversation:

1. **Sample rate**: 50 Hz (current) or 100 Hz? The "50 Hz is standard" argument has support, but other devices (Pedar-X, Moticon OpenGO) sample at 100 Hz internally. With FFT-based storage, the cost of a higher rate is just more compute, not more flash. Lean toward 100 Hz unless the CPU budget is too tight.
2. **FFT type**: full DFT, sliding-DFT, Goertzel, or Welch's method? Each has different RAM/CPU/accuracy tradeoffs. Needs a numerical-methods sanity check -- possibly worth a 1-day prototype.
3. **3000 coefficient count**: an arbitrary upper bound from the discussion. The real number depends on sample rate and target error rate, and is probably much smaller in practice (e.g. 256-512 bins capture everything below 25 Hz at a 50 Hz sample rate).
4. **Slot count and flush interval**: 10 slots x 3 s = 30 s recoverable. Adequate, or do we want longer?
5. **Outlier definition**: sigma threshold? Peak-of-derivative? Domain-specific (e.g. heel-strike acceleration peak)? Pin this down before implementation.
6. **Pause trigger**: AP station count (current plan) or explicit JS heartbeat? Station count is simpler but treats "client on AP, not viewing page" as "connected."
7. **Time sync**: decided -- duration is read from the latest valid flash slot, not from `millis()`. No wall-clock RTC needed unless runs span deep-sleep, in which case slot timestamps would need to be deep-sleep-resilient (RTC, or `boot_count` + relative offset).

## What this means for the team

- **Firmware**: adds the three new modules above; this is the biggest piece of work.
- **Frontend**: simpler, not more complex. The 5 Hz polling JS goes away, the `sensorData` array goes away, and CSV export goes away. The page just renders what `/api/run-state` and `/api/run-report` return.
- **Hardware/electrical**: no change.
- **Mechanical**: no change.
